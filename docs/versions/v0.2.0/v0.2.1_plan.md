# 0.2.1 계획: 첫 세션 업로드 실패 수정과 서버 유휴 완화 검토

작성 2026-10-21. 구현은 하지 않았고 계획과 조사만 적는다. 배경과 결정(A안: 0.2.0을 그대로 Promote하고 0.2.1에서 수정)은 DEVLOG 2026-10-21 항목에 있다.

## 1. 문제 요약
- 현상: 서버(Render)가 한동안 요청을 받지 않은 뒤의 **첫 업로드**가 실패한다. 설치 직후만의 문제가 아니다.
- 가장 가능성 높은 원인(확정 아님): 서버가 깨어나는 데 약 23초가 걸리는데 업로드 시간 제한이 10초(`DEFAULT_TIMEOUT_SECONDS`). 실패하면 요약은 메모리의 `pending_summary`에만 남고, 앱을 닫으면 사라진다.
- 0.2.0에서는 요약이 **로컬 기록**(`%LOCALAPPDATA%\FitRoute\workout_logs\`)에 남는다. 서버에는 올라가지 않을 뿐이다.
- 회귀가 아니다(0.1.1과 같은 코드 경로).

## 2. 0.2.1 항목

| # | 항목 | 위험 | 테스트 방법 |
|---|---|---|---|
| 1 | **업로드를 화면 루프 밖(백그라운드 스레드)으로 이동**, 상태(SAVING/SAVED/FAILED)는 기존 화면 표시로 | 스레드와 `pending_summary` 경쟁, 종료 시 스레드가 도는 중인 경우. 한 번에 하나만 업로드하는 규칙 유지, 종료에서 대기(join) 시간 상한 필요 | 느린 가짜 클라이언트로 `complete_session`이 즉시 반환하는지, 상태 전이, 연속 호출 시 직렬화, 종료 시 대기. 카메라 없이 단위 테스트로 가능 |

권장 범위: **1~5는 클라이언트·런처만 바꾸는 0.2.1**(서버 변경 없음). **6은 서버 변경을 포함하므로 별도 판단**(0.2.1에 넣으려면 서버 멱등 처리를 먼저 배포, 아니면 0.3.0 후보).

0.2.1 릴리스 절차 영향: AI Client 실행 파일과 런처가 바뀌어 검증기 고정값(번들 크기·SHA-256, 런처 해시)을 갱신하고, 번들 재빌드(약 5분)·설치 파일 빌드(약 12분)·Prepare·R2 업로드·업로드본 설치 테스트를 다시 한다. 이미 올라간 0.2.0 객체는 불변이라 그대로 두고 삭제하지 않는다.

## 3. 서버 유휴 완화 검토 (조사만, 구현 없음)

**아래 Render·GitHub·외부 서비스의 한도와 정책은 일반적으로 알려진 값이고 이 저장소에서 확인한 것이 아니다. 실제 값은 Render 대시보드(플랜), 각 서비스 문서에서 확인해야 한다.**

### 3.1 아이디어
외부에서 `GET https://fitroute-api.onrender.com/health`를 일정 간격으로 호출해 서버가 잠들지 않게 한다. `/health`는 DB를 건드리지 않고 `{"status":"ok"}`만 반환한다(`backend/app/routers/health.py`). 따라서 **Render 유휴만 막고, Supabase 무료 프로젝트의 비활성 일시정지는 막지 못한다.**

### 3.2 필요한 호출 간격
- Render 무료 웹 서비스는 일반적으로 약 15분 동안 들어오는 요청이 없으면 정지한다. 호출 간격은 그보다 충분히 짧아야 하고 **10분 안팎**을 권한다(지연·실패 한 번의 여유). 하루 약 144회.
- 정지 후 첫 응답은 이번 측정에서 약 23초였다.

### 3.3 무료 플랜 시간 한도와의 관계
- 무료 인스턴스는 일반적으로 워크스페이스당 월 750시간이다. 서비스 하나를 계속 깨워 두면 한 달(720~744시간)에 거의 전부를 쓴다.
- 같은 워크스페이스에 다른 무료 서비스가 있으면 시간을 나눠 쓴다. 한도를 넘으면 그 달 남은 기간 서비스가 중단될 수 있어, **콜드 스타트보다 더 나쁜 결과**가 된다.
- 사용자가 대시보드에서 확인할 것: 현재 플랜(무료/유료), 이번 달 사용 시간, 같은 워크스페이스의 다른 서비스 유무. 유료 인스턴스는 유휴 정지가 없어 근본 해결책이다.

### 3.4 방식 비교

| | 외부 모니터링/크론 서비스 (예: UptimeRobot, cron-job.org 같은 곳) | GitHub Actions 예약 실행 |
|---|---|---|
| 정시성 | 좋다. 보통 1~5분 간격을 지원 | 나쁘다. `schedule` 실행은 부하 때 몇 분~수십 분 늦거나 건너뛸 수 있다. 10분 간격으로 걸어도 실제 간격이 15분을 넘어 서버가 잠드는 일이 생긴다 |
| 설정 | 계정 만들고 URL 등록. **저장소 변경과 main push가 필요 없다** | 워크플로 파일을 저장소에 추가해야 한다. **예약 실행은 기본 브랜치(main)의 파일만 돌아가므로 main push가 또 필요하다** |
| 비용 | 무료 플랜의 간격·용도 제한 확인 필요 | 공개 저장소는 무료. 비공개 저장소는 월 무료 분량(분 단위 과금)을 넘길 수 있다: 10분 간격이면 월 약 4,300회 실행 × 최소 1분 과금 |
| 부가 | 장애 알림(가동 확인) 기능이 있다 | 저장소에 60일 활동이 없으면 예약 실행이 자동 비활성화될 수 있다 |
| 단점 | 제3자 계정·약관 의존, 무료 플랜 약관 변경 가능성 | 위 정시성, 설정 변경이 코드 이력에 남고 push 필요 |

### 3.5 의견
- 완화일 뿐 근본 해결이 아니다. 배포·재시작 직후와 월 시간 한도 소진 시에는 여전히 콜드 스타트가 생긴다.
- 웹 대시보드도 같은 API를 쓰므로 키프얼라이브는 웹 사용자에게도 도움이 되지만, **앱 쪽 수정(1~4번)이 우선**이다. 3번(런처 사전 호출)은 서버가 필요한 사용자에게만 한 번 호출해 시간 한도를 쓰지 않는다.
- 쓴다면 저장소 변경이 없는 **외부 서비스 방식**이 덜 번거롭고 정시성이 낫다. 단, 3.3의 시간 한도를 먼저 확인해야 한다. 근본 해결은 유료 인스턴스.

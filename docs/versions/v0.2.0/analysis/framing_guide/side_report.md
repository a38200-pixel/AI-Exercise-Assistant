# 좌우 구도 안내 기준 변경 (live_check_phase3 이상 보고 대응)

## 1. 실시간 확인 결과 (`session_20261019_200111_normal_side.jsonl`, note `live_check_phase3`)
- 지시문의 파일명·횟수 칸이 비어 있어 로그에서 확인했다: **실제 6 / 화면 6 / 검출 6**(반복 후보 8개: 확정 6, `shallow_hip_drop`만으로 탈락 2 → 얕음 안내). 프레임 3,554개, 207초.
- 사용자 보고: 범위 안내, 점수 한 줄과 "깊이·상체", 하프 스쿼트 피드백, 얕음 안내(카운트 안 오름), "뒤로 물러서 주세요" 정상. 물러선 위치에서 반복 사이 구도 안내 깜빡임 문제 없음.
- **이상**: "화면 가운데로 이동해 주세요"가 측면 자세에서 앞뒤로 걸어 가장자리로 가도 화면을 거의 나가기 전까지 뜨지 않았다.

## 2. 원인
1. **기준이 너무 늦었다.** 이전 기준은 bbox가 좌우 경계 **2px 이내**일 때였다. 그런데 판정용 crop은 bbox 양옆으로 폭의 30%(이 로그에서 약 30~40px)를 더해 만든다. 몸이 경계에서 40px 떨어진 지점에서 이미 crop이 잘리기 시작한다.
2. 로그의 해당 구간(**170~177초**, 멀리 선 위치에서 오른쪽으로 걸어감): bbox 오른쪽 x2가 490 → 604 → **621**(프레임 폭 640, 경계까지 19px)까지 갔고(crop 잘림 0.31~0.34), 이전 기준(x2 ≥ 638)은 한 번도 안 켜졌다. 이 구간에서 화면에 뜬 구도 안내는 없었다(로그 `rep.framing`이 모두 None).
3. 그 밖의 가장자리 접근(4~30초, 39~43초, 157~163초, 183~193초, 207~209초)은 모두 **가까이 선 위치**(몸 높이가 화면의 98~100%, 발 아래 여유 0~8px)였다. 이때는 아래·높이 조건이 우선이라 "뒤로 물러서 주세요"가 뜨고(총 1,803프레임), "화면 가운데로"는 6프레임뿐이었다(약 7~10초).
4. **별개의 결함도 찾아 고쳤다**: 이 로그의 4~10초에 구도 안내가 0.1~0.5초 간격으로 켜졌다 꺼졌다 했다. YOLO가 사람을 한두 프레임 놓칠 때 안내가 곧바로 꺼졌기 때문이다(상태는 유지되는데 화면 표시만 None을 돌려줌). 사람을 놓친 프레임에서도 안내를 이어서 보이게 고쳤다(2초 넘게 안 보이면 거둠, 반복 중에는 숨김).

## 3. 새 기준: "판정용 crop의 좌우 잘림 정도"
- 정의: `잘림 = (여유 중 프레임 밖으로 나간 길이) / 여유`, 여유 = bbox 폭 x 0.30(`BBOX_PADDING`). 왼쪽·오른쪽 중 큰 쪽. 0 = 여유가 다 있음, 1 = bbox가 경계에 닿음(이전 기준 2px은 약 0.95).
- **임계값은 공백 분석 데이터(로그 17개, YOLO가 사람을 찾은 프레임)로 정했다**: crop 잘림 정도별 landmark 공백(pose_miss) 비율.

| 잘림 정도 | 전체 프레임 수 | 공백 비율 | 세로 조건이 정상인 프레임만 | 공백 비율 |
|---|---|---|---|---|
| 0 (여유 다 있음) | 17,346 | 7.8% | 14,124 | 3.3% |
| 0 초과 ~ 0.25 | 428 | 75.0% | 8 | 0.0% |
| 0.25 ~ 0.5 | 503 | 62.0% | 46 | 0.0% |
| 0.5 ~ 0.75 | 194 | 62.4% | 1 | 100% |
| 0.75 ~ 0.95 | 540 | 78.1% | 6 | 83.3% |
| 0.95 이상 | 2,515 | 75.8% | 104 | 74.0% |

- **해석**: 전체 표(왼쪽)의 높은 공백률은 대부분 "가까이 서서 아래도 잘리는" 프레임과 겹친 것이다. 좌우 효과만 보려고 아래·높이 조건이 정상인 프레임만 보면(오른쪽), **잘림이 0.5 미만일 때 공백은 0%(54프레임)이고, 0.75 이상에서 74~83%**다. 0.5~0.75 구간은 표본이 1프레임뿐이라 데이터로는 0.5와 0.75를 가를 수 없다.
- **채택: 0.5**(`FRAMING_SIDE_CROP_CUT_RATIO`). 공백이 시작되기 전에 안내하되(이전 기준 2px보다 훨씬 일찍: 몸이 경계에서 폭의 약 15%(20px) 안으로 들어왔을 때), 안내가 켜진 프레임의 85%가 실제 공백인 값이다.

## 4. 로그 재생 (지속 1.5초, 해제 0.5초, 반복 중 미표시)
`python -m scripts.analysis.framing_replay --log data/landmark_sequences/session_2026*.jsonl --delays 1.5 --compare-side`

좌우 조건만 본 비교(아래·높이 조건은 끄고, 세로 조건이 정상인 프레임 기준):

| 기준 | 켜진 프레임 | 그중 공백 비율 | 공백 프레임 중 포착 | 세트 안 켜진 구간 수 | 길이 중앙값/최대 |
|---|---|---|---|---|---|
| crop 잘림 ≥ 0.25 | 117 | 64% (75/117) | 14% (75/550) | 4 | 1.8s / 7.7s |
| **crop 잘림 ≥ 0.5(채택)** | 87 | **85% (74/87)** | 13% (74/550) | **1** | 7.5s / 7.5s |
| crop 잘림 ≥ 0.75 | 87 | 85% (74/87) | 13% (74/550) | 1 | 5.9s / 5.9s |
| crop 잘림 ≥ 0.95(이전 2px에 가까움) | 87 | 85% (74/87) | 13% (74/550) | 2 | 3.0s / 3.0s |

- **이전 기준과의 차이는 거의 없다**(공백 비율 85%, 포착 13%로 같음). 세로 조건이 정상인 프레임 중 공백의 대부분(87%)은 좌우와 무관한 다른 원인이다.
- 세로 조건까지 합친 실제 안내(총 6,679프레임이 켜짐, 그중 공백 55.1%, 공백 프레임의 83.0% 포착)도 이전 기준(≈0.95)과 새 기준(0.5)이 **똑같다**: 좌우 가장자리 근처의 프레임은 거의 모두 가까이 서서 이미 아래·높이 조건이 켜져 있기 때문이다. 좌우 기준이 달라지는 경우는 **멀리 서서 옆으로만 걸어 경계로 가는** 드문 상황(이번 보고의 170~177초)뿐이다.
- **세트 안(정상 반복 사이)에 켜지는 구간**(좌우 조건만, 0.5 기준): **1구간** — 시험 세션(`20261018_135535`) 38.0~45.5초 7.5초, 공백 138/167프레임(몸이 경계에 걸려 실제로 공백이 많았던 구간이라 옳은 안내). 0.25로 낮추면 4구간(추가: `live_check_phase3` 160.4~162.2초 공백 15/33, **174.7~176.4초 공백 0/29(사용자가 가장자리로 간 구간)**, 189.6~190.7초 공백 12/22). 자주 뜨지는 않는다.

## 5. live_check_phase3에서 사용자가 가장자리로 간 구간(170~177초)에서 새 기준이 안내하는 시점
| 기준 | 안내 구간 |
|---|---|
| 이전(2px) | 없음 |
| crop 잘림 ≥ 0.95, 0.75, **0.5(채택)** | **없음**(이 구간의 최대 잘림이 0.34) |
| crop 잘림 ≥ 0.25 | 174.7 ~ 176.4초(1.7초) |

- **새 기준 0.5도 이 구간(최대 잘림 0.34)은 안내하지 않는다.** 데이터로 보면 이 구간은 포즈 인식이 정상이었고(해당 프레임 공백 0) 잘림 0.5 미만에서는 공백이 거의 없었다. 즉 "공백을 피하려는 안내"로서는 이 구간이 안내 대상이 아니다.
- 사용자의 기대("가장자리로 가면 더 일찍")를 따르려면 **0.25**로 낮춰야 하고 그러면 이 구간이 174.7초부터 켜진다. 대가: 켜진 프레임의 공백 비율 85% → 64%, 세트 안 켜지는 구간 1 → 4. **값 한 줄(`FRAMING_SIDE_CROP_CUT_RATIO`) 변경으로 바꿀 수 있고, 어느 쪽을 쓸지는 사용자 결정이다.** (공백 데이터 기준으로 정하라는 지시에 따라 0.5를 썼다.)

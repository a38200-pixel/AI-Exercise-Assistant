# E 키(세션 종료)로 세션 요약이 서버에 올라갔는지 확인 (2026-10-20)

사용자 진술: 1차(본인), 2차(P01), 3차(P02) 실측과 실시간 확인 세션에서 모두 `E`(세션 종료)를 눌렀고, 2차·3차는 `S`(세션 시작)도 평소 흐름대로 눌렀다. 서버에는 접근하지 않았고 아무것도 삭제하지 않았다(코드와 로컬 파일만 읽었다). 환경 변수는 **있는지 없는지만** 확인했고 값은 출력하지 않았다.

## 1. 코드 경로 (무엇이, 언제 올라가는가)

- `E`: `handle_keyboard_input` → `complete_session` → `workout_session.end(...)`로 요약을 만들고 → **`workout_uploader.submit(summary)`**. 세션이 진행 중일 때 `Q`/`ESC`로 끝내도 같은 `complete_session`이 불린다(그래서 `E`를 누르지 않았어도 `S`로 시작한 세션이 열려 있으면 종료 때 올라간다).
- 올라가는 내용(`WorkoutApiClient.save_workout_session`): `POST {FITROUTE_API_BASE_URL}/api/workouts`에 **요약 6개 키만** — `workout_date`, `started_at`, `ended_at`, `workout_seconds`, `squat_count`, `stretch_seconds`. 인증은 `Authorization: Bearer <FITROUTE_ACCESS_TOKEN>`이라 서버에서는 **토큰 주인의 계정(= 실측을 운영한 계정)** 으로 저장된다. 참여자 코드, 이름, 반복별 자세 점수, 좌표는 올라가지 않는다.
- **업로드가 일어나는 조건**: 앱을 실행한 프로세스에 `FITROUTE_ACCESS_TOKEN`이 설정되어 있어야 한다(`create_api_client_from_environment`). 없으면 시작 때 `[Cloud] FitRoute API token not configured.` / `Workout sessions will not be uploaded.`가 출력되고, `E`마다 `[Cloud] Upload disabled. FITROUTE_ACCESS_TOKEN is not configured.`가 출력되며 **네트워크 요청은 하지 않는다.**
- 주소: `FITROUTE_API_BASE_URL`이 없으면 기본값 **`http://127.0.0.1:8000`**(이 PC의 개발 서버). 토큰만 설정했다면 로컬 개발 서버로 갔고, 그 서버가 꺼져 있었다면 연결 실패다.
- **연결 실패·검증 실패 시**: 요약이 `pending_summary`에 남고(`[Cloud] ... server save failed`, `Press P to retry`), 그 상태에서 다음 `E`는 `[Cloud] A previous workout is still pending. Press P to retry it first.`만 출력하고 **새 요약을 올리지 않는다.** 즉 서버가 닫혀 있었다면 첫 세션 요약만 대기 상태였을 것이다.
- 이번 실측은 `python -m src.main`(개발 실행)이다. 설치판 런처가 토큰을 넘기는 경로는 쓰이지 않았다.

## 2. 이 PC에서 확인된 것과 확인할 수 없는 것

| 확인 | 결과 |
|---|---|
| `FITROUTE_ACCESS_TOKEN` (Windows 프로세스·사용자·시스템 환경) | **설정 안 됨** |
| `FITROUTE_API_BASE_URL` (같은 세 범위) | 설정 안 됨(기본 `127.0.0.1:8000`) |
| 저장소 루트 `.env` | 없음 |
| 로컬 운동 기록(`workout_*.json`)에 업로드 결과(세션 id, 성공·실패)가 남는가 | **남지 않는다**(요약 6개 키 + 반복별 결과 + 설정만). 터미널 출력(`[Cloud] ...`)도 파일로 저장되지 않는다 |

→ **이 PC의 영구 설정으로는 업로드가 꺼져 있다.** 다만 실측 때 쓴 터미널에서 토큰을 **그 창에서만** 임시로 설정했다면(`$env:FITROUTE_ACCESS_TOKEN=...`) 저는 볼 수 없다. 로컬 로그만으로는 업로드 여부를 **확정할 수 없다.** 가장 빠른 확인은 실측 때 터미널 첫 줄들의 `[Cloud]` 출력("token not configured"인지 "upload is ready"인지)과, 서버(또는 로컬 개발 서버의 DB)에 아래 시각의 행이 있는지다.

## 4. 판단

- **이 PC의 영구 설정으로는 업로드가 꺼져 있었고, 로컬 로그로는 업로드를 확인할 수 없다.** 업로드됐다면 임시로 토큰을 설정한 터미널에서 실행했을 때뿐이며, 그 경우에도 기본 주소가 로컬 개발 서버(`127.0.0.1:8000`)라 그 서버가 켜져 있었어야 한다. 서버가 켜져 있지 않았다면 첫 요약 하나만 대기 상태였을 것이다.
- 업로드됐을 가능성이 가장 구체적인 쪽은 3.1과 3.2의 정확한 값 19건이다(참여자 식별 정보는 담지 않지만 동의 범위 밖). 확인은 **실측 때 터미널의 `[Cloud]` 출력**(`not configured`였는지)과 서버 DB의 위 시각 행으로 하는 것이 가장 빠르다.
- 다음에는 실측 때 `S`·`E`를 누르지 않게 하거나, 토큰을 설정하지 않은 셸에서 실행하는 것이 안전하다(진행표 준비 체크리스트에 "`FITROUTE_ACCESS_TOKEN`이 설정되지 않았는지"를 넣는 것을 제안한다. 본인 확인용 진행표에는 이미 넣는다).

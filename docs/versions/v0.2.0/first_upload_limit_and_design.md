# 첫 업로드 실패: 한계와 예상 해결 방안 (설계 수준)

작성 2026-10-21. **0.2.0의 한계로 문서화하며 이번에는 고치지 않는다.** 아래 해결 방안은 구현 계획이 아니라 나중에 고친다면 어떻게 할지에 대한 설계 수준의 기록이다. 배경과 결정은 DEVLOG 2026-10-21 항목에 있다.

## 1. 한계

- **현상**: 서버(Render)가 한동안 요청을 받지 않은 뒤의 **첫 업로드**가 실패할 수 있다. "설치 직후"의 문제가 아니라 "서버가 쉬고 난 뒤 첫 업로드"의 문제다.
- **가장 가능성 높은 원인(확정 아님)**: 서버가 한동안 요청을 받지 않으면 잠들고, 깨어나는 데 약 23초가 걸린다. 업로드 시간 제한은 10초(`DEFAULT_TIMEOUT_SECONDS`)이고 요청은 재시도 없이 한 번만 보낸다. 실패한 요약은 메모리의 `pending_summary`에만 있어 앱을 닫으면 사라진다. 실패 당시 앱 메시지를 확인하지 못해 확정하지는 못했다.
- **0.1.1부터 있던 동작**이며 0.2.0의 회귀가 아니다(`src/api_client.py`, 런처, 백엔드는 0.1.1 릴리스 커밋과 코드가 같다).
- **0.2.0에서는** 실패한 세션도 로컬 기록 파일(`%LOCALAPPDATA%\FitRoute\workout_logs\workout_<시작시각>.json`)로 남는다.
- **사용자 안내**: 처음 접속할 때 서버가 깨어나는 데 시간이 걸릴 수 있다. 첫 세션 기록이 웹에 보이지 않으면 서버가 깨어난 뒤의 세션부터 정상 저장된다.
- 관측: 2026-10-21 R2 업로드본 설치 테스트에서 첫 세션 업로드 실패, 같은 설치 상태의 두 번째 세션(첫 요청이 서버를 깨운 뒤 약 11분 뒤)은 성공. 2026-10-20 스모크 세션 성공은 직전 0.1.1 세션에서 8분 뒤였다.

## 2. 예상 해결 방안 (설계 수준)

| 방안 | 해결하는 부분 | 위험 |
|---|---|---|
| 업로드를 화면 루프 밖(백그라운드)으로 이동하고 시간 제한 상향(연결은 짧게, 읽기는 60초 안팎) | 서버가 깨어나는 동안 기다려 첫 요청이 성공한다. 화면은 멈추지 않는다. 시간 제한만 올리면 창이 20초 이상 멈추므로 둘은 함께여야 한다 | 스레드와 `pending_summary` 경쟁, 종료 시 진행 중 스레드 처리 |
| 런처가 로그인(토큰 확보) 직후 `/health`를 백그라운드로 사전 호출 | 로그인 대기(수 초~20초) 동안 서버가 먼저 깨어난다. 앱 쪽 변경 없이 효과가 크다 | 런처 실행 파일 변경(설치 검증의 해시 고정값 갱신). 토큰을 보내지 않으며 실패는 무시 |
| 종료 시 대기 요약 재시도 또는 알림 | 앱을 닫아서 요약이 사라지는 부분을 막는다(재시도하거나 최소한 "저장되지 않았습니다"를 알림) | 닫기가 늦어지는 느낌(강제 종료 경로 필요) |
| 업로드 결과 파일 로그 | 실패 원인을 사후에 확인할 수 있다(지금은 콘솔 `print`뿐이라 창을 닫으면 사라진다) | 로그 크기 관리, 토큰·본문 기록 금지 |
| 로컬 기록 재전송(성공 표시 + 서버 중복 방지) | 이미 남아 있는 로컬 기록에서 실패한 세션을 나중에 서버로 올린다 | **가장 큼.** `workout_sessions`에 `(user_id, started_at)` 유일 제약이 없고 일일 요약 RPC가 값을 더하므로, 중복 전송은 중복 행·이중 합산을 만든다. 서버 멱등 처리(스키마·RPC 변경)가 먼저 필요하고 0.2.0 기록에는 업로드 상태가 없어 성공·실패를 구별할 수 없다 |
| 서버를 주기 호출로 깨워 두는 운영 방식(아래 3절) | 서버가 잠들지 않아 모든 사용자(앱·웹)의 첫 요청이 빨라진다. 코드 변경 없이 가능 | 무료 플랜 월 시간 한도 소진, 외부 서비스·약관 의존, 배포·재시작 직후에는 여전히 콜드 스타트 |

## 3. 서버 유휴 완화 검토 (운영 방식, 조사만)

**아래 Render·GitHub·외부 서비스의 한도와 정책은 일반적으로 알려진 값이고 이 저장소에서 확인한 것이 아니다. 실제 값은 Render 대시보드(플랜), 각 서비스 문서에서 확인해야 한다.**

- **아이디어**: 외부에서 `GET https://fitroute-api.onrender.com/health`를 일정 간격으로 호출한다. `/health`는 DB를 건드리지 않고 `{"status":"ok"}`만 반환하므로(`backend/app/routers/health.py`) Render 유휴만 막고, Supabase 무료 프로젝트의 비활성 일시정지는 막지 못한다.
- **간격**: Render 무료 웹 서비스는 일반적으로 약 15분간 요청이 없으면 정지한다. **10분 안팎**을 권한다(하루 약 144회).
- **무료 시간 한도**: 무료 인스턴스는 일반적으로 워크스페이스당 월 750시간이다. 서비스 하나를 계속 깨워 두면 한 달(720~744시간)에 거의 전부를 쓰고, 다른 무료 서비스가 있으면 시간을 나눠 쓴다. 한도를 넘으면 그 달 남은 기간 서비스가 중단될 수 있어 콜드 스타트보다 나쁘다. 사용자가 대시보드에서 플랜·사용 시간·같은 워크스페이스의 다른 서비스를 확인해야 한다. 유료 인스턴스는 유휴 정지가 없다.

| | 외부 모니터링/크론 서비스 (예: UptimeRobot, cron-job.org) | GitHub Actions 예약 실행 |
|---|---|---|
| 정시성 | 좋다. 보통 1~5분 간격 지원 | 나쁘다. `schedule`은 부하 때 몇 분~수십 분 늦거나 건너뛸 수 있어 15분을 넘겨 서버가 잠들 수 있다 |
| 설정 | 계정 만들고 URL 등록. 저장소 변경과 main push가 필요 없다 | 워크플로 파일 추가가 필요하다. 예약 실행은 기본 브랜치(main)의 파일만 돌아가므로 main push가 또 필요하다 |
| 비용 | 무료 플랜의 간격·용도 제한 확인 필요 | 공개 저장소는 무료. 비공개 저장소는 월 약 4,300회 × 최소 1분 과금으로 무료 분량을 넘길 수 있다 |
| 부가 | 장애 알림 기능 | 저장소에 60일 활동이 없으면 예약 실행이 자동 비활성화될 수 있다 |
| 단점 | 제3자 계정·약관 의존 | 위 정시성, 설정 변경이 코드 이력에 남고 push 필요 |

쓴다면 저장소 변경이 없는 외부 서비스 방식이 덜 번거롭고 정시성이 낫다. 단 시간 한도를 먼저 확인해야 하며 완화일 뿐 근본 해결이 아니다(배포·재시작 직후와 시간 한도 소진 시에는 여전히 콜드 스타트). 근본 해결은 유료 인스턴스다.
